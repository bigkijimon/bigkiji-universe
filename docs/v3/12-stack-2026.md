## 2. MCP — Model Context Protocol

**State of the art.** The 2026-07-28 revision is the largest since launch: a stateless
core, Multi Round-Trip Requests, and an extension framework
(https://blog.modelcontextprotocol.io/posts/2026-07-28/). Authorization remains OAuth
2.1-based; Dynamic Client Registration (RFC 7591) is being deprecated in favor of
Client ID Metadata Documents (CIMD); Resource Indicators (RFC 8707) and PKCE are
required (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization,
https://workos.com/blog/mcp-2026-spec-agent-authentication). Two transports: stdio —
newline-delimited JSON-RPC, specified in only a handful of requirements — and
Streamable HTTP, which carries session-ID management and 404-triggered re-initialization
(https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). Known
threat classes: Tool Poisoning (malicious instructions in tool descriptions, invisible
to users but read by the LLM), indirect prompt injection via tool results, Confused
Deputy, and Rug Pull (definitions changing after approval); OWASP maintains an MCP
security cheat sheet and a Top 10
(https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html).

**Applicability.** BigKiji currently has **zero** MCP surface by design: no
`@modelcontextprotocol` dependency exists, and spawned providers are denied `mcp__*`
tools at four layers (`src/domain/pi-core/security/tool-interceptor.js:21`,
`src/domain/pi-agent/task-runner.js:249` empty `mcpServers` + `:276`
`--strict-mcp-config` + `:278` `--disallowed-tools`). The stdio transport is small
enough that a dependency-zero client (`child_process.spawn` + `readline` + a request-id
`Map`) is low-difficulty, while the HTTP transport and the whole OAuth/CIMD stack exist
to solve problems — cross-org identity, remote servers — that a single-machine app does
not have.

**Verdict: Conditional No.** Owner decision (2026-08-02): stdio, 127.0.0.1,
owner-installed trusted servers only; no external MCP servers, no OAuth 2.1, no
Streamable HTTP; the `mcp__` denial for provider children stays. Full security design
in `09-security.md` §6.

## 3. A2A — Agent2Agent

**State of the art.** Announced by Google 2025-04, moved to the Linux Foundation
2025-06, v1.0 finalized 2026-04-09; 150+ organizations, native integrations in Azure AI
Foundry, Amazon Bedrock AgentCore, and Google Cloud
(https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year,
https://en.wikipedia.org/wiki/Agent2Agent). Its headline feature is the Signed Agent
Card at `/.well-known/agent-card.json`. Division of labor per the ecosystem: MCP =
agent→tool, A2A = agent→agent (https://www.truefoundry.com/blog/mcp-vs-a2a).

**Applicability.** A2A's core value is discovery and trust establishment *between
organizations*. BigKiji's workers are child processes whose topology is fully known at
spawn time (`task-runner.js` builds each adapter and its policy itself,
`task-runner.js:273-292`); there is nothing to discover and no cross-org trust to
establish. Adopting A2A would add a network protocol precisely where `09-security.md`
works to keep the surface at zero.

**Verdict: No (overkill).** Revisit only if BigKiji ever federates with agents it does
not itself spawn.

## 4. Context engineering

**State of the art.** Chroma's "Context Rot" benchmark across 18 models shows accuracy
degrading consistently as input length grows, even on simple tasks; tool-count findings
report visible accuracy loss **beyond ~10 tools** and ~50K tokens of overhead at 90
tools. The "Lost in the Middle" result (Stanford, Liu et al., TACL 2024) still holds in
2026. The standard pattern is a sliding window plus LLM summarization hybrid; Manus'
practitioner findings add: keep the most recent tool calls raw (preserves formatting
rhythm) and **never compress error information**
(https://www.newsletter.swirlai.com/p/state-of-context-engineering-in-2026,
https://pub.towardsai.net/state-of-context-engineering-in-2026-cf92d010eab1).

**Applicability.** BigKiji already satisfies the headline conditions:

- **6 tools** are exposed to the Claude worker — `Read,Edit,Write,Bash,Grep,Glob`
  (`task-runner.js:278`) — under the ~10-tool threshold.
- The conversation engine already runs a window-plus-compaction scheme
  (`src/domain/pi-core/conversation-engine.js:130` `compact()`, history capped at
  `maxTurns`).
- The context pruner slices files under a token budget rather than shipping whole
  trees (`src/domain/pi-agent/context-pruner.js`).

V3 adoptions: keep tool count at or near 6 (MCP tools from §2 must be counted against
this same budget, not added freely); keep recent tool outputs verbatim in Pi context;
exempt error text from all compaction paths.

**Verdict: Unconditional Yes** — mostly ratifying existing behavior, with the
error-compression prohibition made explicit.

## 5. GraphRAG vs. plain retrieval

**State of the art.** Plain vector RAG suffices when answers live in one or two
passages; GraphRAG pays off when answers depend on multi-hop relations across the
corpus. Indexing costs have fallen (LazyGraphRAG near vector-RAG cost; LightRAG
similar), while full Microsoft GraphRAG still runs $5–20 on mid-size corpora
(reproducibility unconfirmed — §9). One outlet offers "plain vector RAG holds up to
~100K documents" as a rule of thumb (single-source, weak confidence — §9). Separately
and better-evidenced: **hybrid search (BM25 + dense vectors + RRF fusion + cross-encoder
rerank) beats pure dense retrieval in nearly all 2024-2025 benchmarks**; one measured
comparison reports Recall@5 = 0.816 (hybrid + rerank) vs 0.587 (pure dense). BM25 and
cosine scores are not on one scale, so fuse by RRF, not weighted sums
(https://aloknecessary.github.io/blogs/graph-rag-vs-rag/,
https://arxiv.org/html/2604.01733v1).

**Applicability.** BigKiji's corpus is a personal vault, orders of magnitude below any
threshold where GraphRAG differentiates; the vault already has a separate knowledge
graph (graphify) for relationship queries. The cheap, evidenced win is hybrid lexical +
dense retrieval with RRF for local search, feeding the same bge-m3 embeddings adopted
in §7.

**Verdict: No** to GraphRAG; **Yes** to lightweight hybrid search (BM25 + bge-m3 dense
+ RRF, optional cross-encoder rerank) as the local retrieval upgrade.

## 6. Semantic cache

**State of the art.** Practitioner starting thresholds are cosine 0.90–0.95 (Redis;
Databricks uses 0.92) (https://redis.io/blog/what-is-semantic-caching/,
https://portkey.ai/blog/semantic-caching-thresholds/). The MeanCache paper measured
that the *optimal* threshold differs per embedding model (MPNet 0.83, Albert 0.78;
GPTCache's suggested 0.7 was suboptimal) — meaning thresholds must be tuned on one's
own system, not copied (https://arxiv.org/pdf/2403.02694). The best-evidenced guard
against false hits is a cross-encoder second-stage verification (60–80% false-hit
reduction; 15–30 ms with MiniLM-L-6-v2). False hits cost more than false misses — the
asymmetry should be designed in.

**Applicability.** BigKiji has a task cache with per-entry hit counting
(`src/domain/pi-agent/task-cache.js:141`) but no embedding-based matching and — as
`10-performance.md` §7 T6 notes — no miss counting, so no measurable hit rate yet.
A semantic layer only makes sense once bge-m3 (§7) is wired in, and its threshold must
be tuned against BigKiji's own query distribution (per MeanCache), starting from 0.92
and validated with a cross-encoder check on hits. Whether BigKiji's real query stream
has enough near-duplicates to reach the 90% hit-rate target is unknown (§9).

**Verdict: Conditional Yes** — gated on embedding adoption, local threshold tuning,
and hit/miss instrumentation existing first.

## 7. Embedding model selection

**State of the art (candidates).**

| Model | Key facts | Source |
|---|---|---|
| nomic-embed-text | Most-pulled on Ollama (~73.8M), 768-dim, 274MB, English-centric design; Ollama v0.30 changed behavior to lowercase inputs | https://www.tigerdata.com/blog/finding-the-best-open-source-embedding-model-for-rag |
| **bge-m3** | MIT license, 100+ languages, 8K context, dense/sparse/multi-vector in one model; cited as "the default self-hosted production RAG stack of 2026" together with BGE-reranker-v2 | https://www.tigerdata.com/blog/finding-the-best-open-source-embedding-model-for-rag |
| Qwen3-Embedding | Apache-2.0, 0.6B/4B/8B, official Ollama; 8B ranked #1 on MTEB multilingual (70.58) as of 2025-06-05; 256–2048 variable dims | https://ollama.com/library/qwen3-embedding |
| Ruri v3 310M (cl-nagoya) | Japanese-specialized; JMTEB 77.24 vs OpenAI text-embedding-3-small 70.86; **not** in the official Ollama library — manual GGUF import required | https://huggingface.co/cl-nagoya/ruri-v3-310m |

No direct JMTEB comparison of bge-m3 vs Qwen3-Embedding vs Ruri v3 was found (§9).

**Decision.** **Owner decision (2026-08-02): bge-m3**, already pulled locally.
Rationale: multilingual coverage matching a Japanese/English mixed vault, permissive
license, native support for the dense+sparse duality that §5's hybrid retrieval wants,
and zero manual-import friction. Ruri v3 remains the candidate to benchmark against
*on this vault's own data* if Japanese retrieval quality proves insufficient — a local
eval, not a leaderboard transfer.

## 8. Multi-agent architecture

**State of the art.** The 2026 consensus: strengthen a single agent first; go
multi-agent only after hitting a clear ceiling. Measured (arXiv 2604.00073):
Planner-Executor on weaker models 74.8% vs 73.3% single-agent — a ~1.5pp gain for
**+48% cost**; on stronger models the gap disappears and single-agent wins on cost
(https://arxiv.org/pdf/2604.00073). Practical evaluations find Hierarchical
(Supervisor-Worker) and Graph topologies most cost-effective, with Blackboard/Swarm
rarely showing real-world advantage
(https://www.digitalapplied.com/blog/agent-architecture-patterns-taxonomy-2026).
Supervisor-Worker is reported as ~70% of production multi-agent deployments (industry
survey; rigor unverified — §9). The apparent Cognition-vs-Anthropic contradiction
("Don't Build Multi-Agents" vs "+90.2% on research tasks at 15× tokens") resolves by
task type: read-heavy work parallelizes; write-heavy work needs shared context
(https://news.smol.ai/issues/25-06-13-cognition-vs-anthropic).

**Applicability.** BigKiji already runs the recommended shape: one orchestrator
(`src/domain/pi-agent/task-runner.js` + `model-router.js`) dispatching single-provider
workers, with a capability registry scoring providers
(`model-capability-registry.js`). The 2026 evidence argues for **not** adding
planner/critic/swarm layers: BigKiji's task mix is write-heavy (edits to a vault and a
codebase), exactly the case where multi-agent context-sharing costs bite, and the +48%
cost for ~1.5pp is a bad local trade. The registry's newly repaired learning loop
(`10-performance.md` §6) is the "strengthen the single agent" path.

**Verdict: Conditional Yes** — keep Orchestrator-Workers as-is; invest in routing
quality, not in agent count. Parallel fan-out is acceptable only for read-only
research-style subtasks.
